# Reconciliation AI

Сверка актов сверки с контрагентами на **локальной модели Ollama**.
Переносимое приложение для Windows: один процесс, один порт, никакого Docker.

---

## Что нужно пользователю

1. **Ollama** — установленная и запущенная локальная модель.
2. **Папка приложения** — распакованная как есть (не через zip-архив).

Больше ничего: Node.js внутри приложения, установка зависимостей не требуется.

```bat
ollama pull qwen2.5:7b-instruct
```

Дальше — двойной клик по `start.cmd`. Интерфейс откроется сам.

---

## Настройка: `settings.txt`

Единственный файл конфигурации. Он лежит рядом с `start.cmd`.
Правьте его и перезапускайте приложение — больше нигде ничего менять не нужно.
Файла `.env` и переменных окружения больше не существует.

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `APP_HOST` | `127.0.0.1` | `127.0.0.1` — только с этой машины; `0.0.0.0` — доступ по сети |
| `APP_PORT` | `8080` | Порт приложения и интерфейса |
| `API_BASE_URL` | *(пусто)* | Адрес API для фронтенда. Пусто — запросы идут на тот же origin |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Адрес Ollama |
| `OLLAMA_MODEL` | `qwen2.5:7b-instruct` | Модель. Должна быть скачана: `ollama pull <имя>` |
| `AI_TIMEOUT_SEC` | `30` | Таймаут одного запроса к модели |
| `LOG_LEVEL` | `info` | `error` / `warn` / `info` / `debug` / `trace` |
| `LOG_FILE` | *(пусто)* | Например `logs/app.log`. Пусто — только консоль |
| `OPEN_BROWSER` | `true` | Открывать браузер при старте |

Формат — плоский список `КЛЮЧ=ЗНАЧЕНИЕ`. `#` в начале строки — комментарий,
`#` после пробела тоже считается комментарием. Ключи регистронезависимы.
Неизвестный ключ, некорректное число или неверный URL — приложение не стартует
с понятным сообщением, а не падает молча.

**Смена модели:** отредактируйте `OLLAMA_MODEL`, выполните
`ollama pull <новое имя>`, перезапустите `start.cmd`. Выбирать модель в
интерфейсе нельзя — так исключено расхождение между настройкой и тем, что
реально применилось. Фактическая модель показана в шапке и в `GET /api/health`.

## Режимы работы

Приложение открывается в режиме **«Сверка»** — полный пайплайн:

```
загрузка → разбор (включая OCR сканов) → определение структуры
   → подтверждение структуры → извлечение → сверка → анализ → отчёт
```

Если структура таблицы не распознаётся однозначно, пайплайн останавливается и
ждёт подтверждения: показывает колонки и предлагает, какая за что отвечает.
Прогресс и ход работы видны в реальном времени, задание можно отменить.

Готовый отчёт сохраняется и в `app/reports/`, и доступен из интерфейса:

- `GET /api/jobs/:id/report` — JSON
- `GET /api/jobs/:id/report.html` — HTML для печати и отправки

Второй режим — **«Быстро»**: два файла, разбор и сравнение на одной странице,
с ручным редактированием распознанных данных. Здесь работают только XLSX и PDF
с текстовым слоем; для сканов используйте режим «Сверка».

## Как это устроено

Один процесс Fastify отдаёт и API, и собранный фронтенд из того же origin —
поэтому в браузере интерфейс и API не расходятся по портам, и CORS-настройки
не нужны.

```
dist-portable/
  start.cmd            запуск (двойной клик)
  settings.txt         конфигурация
  README.txt           этот файл
  runtime/node.exe     встроенный Node
  frontend/dist/       собранный интерфейс
  app/                 backend
    src/               исходники TypeScript
    node_modules/      зависимости
    .tessdata/         языковые данные OCR
    logs/              логи
    reports/           отчёты
```

Backend запускается через `tsx` прямо из TypeScript: отделённой сборки
не требуется, а обновление — это замена папки `app/src`.

**Обновление по частям:**

- backend → заменить `app/src/`;
- интерфейс → собрать `pnpm --filter @recon/frontend build` и заменить `frontend/dist/`;
- `settings.txt`, `app/reports/`, `app/logs/` при этом не трогаются.

**Если модель недоступна** (Ollama не запущена или модель не скачана),
приложение не падает: структура определяется эвристиками, сверка считается
обычными правилами, а в лог и в интерфейс попадает причина деградации.
В консоль при старте выводится подсказка — `ollama serve` или `ollama pull`.

## Сборка portable-версии

Собирать нужно **на Windows** в корне репозитория, где есть Node.js 20+ и pnpm:

```bat
build-win.cmd
```

Скрипт установит зависимости, соберёт интерфейс, развернёт backend через
`pnpm deploy` (самодостаточная папка зависимостей без внешних ссылок),
скопирует встроенный `node.exe`, данные OCR и создаст `settings.txt`.
Результат — папка `dist-portable/`, которую копируют целиком.

> Папку нельзя распаковывать из zip-архива: в `node_modules` есть относительные
> ссылки нативных модулей. Переносите каталогом.

## Частые проблемы

**Приложение работает, ошибок нет, но распознавание выглядит «тупо» — результаты
без AI, всё по эвристикам.**
Это не поломка, а штатная деградация (см. «Если модель недоступна» выше): пайплайн
считает эвристиками, и в интерфейсе это неотличимо от нормальной работы. Два
следа, по которым видно, что модели не было:

- **консоль при старте.** Preflight проверяет Ollama и модель до открытия браузера
  и печатает причину: `Ollama недоступна по адресу …`, `Ollama отвечает, но модель
  … не скачана` или `В Ollama пока нет ни одной модели` (`backend/src/preflight.ts`).
  Сообщение — в консоли и в лог, в интерфейс оно не выводится;
- **отчёт.** В обоих форматах (JSON и HTML) есть таймлайн логики `aiLogic`. При
  деградации в нём появляется шаг **«Гипотезы сформированы по правилам»** с
  уточнением, что модель была недоступна. Если такой шаг есть — AI не участвовал,
  арифметика сверки при этом корректна: правила детерминированные.

В интерфейсе других признаков нет: экран подтверждения структуры и отчёт не
показывают, кто определил структуру. Ориентируйтесь на эти два места.

Лечится на месте, пересборка не нужна: запустите Ollama, выполните `ollama pull`
с именем модели из `settings.txt`, перезапустите приложение. Скачанную модель
сверяйте через `ollama list` — имя в `settings.txt` должно совпадать с тегом
дословно, включая версию.

**Ollama отвечает, но первый анализ идёт минуты.**
Это не зависание, а загрузка модели в память: на CPU 30–120 с. Последующие
запросы к той же модели быстрые. Полезное отличие: при недоступной модели анализ,
наоборот, подозрительно быстрый — соединение обрывается сразу.

## Разработка

```bat
pnpm install
pnpm dev          backend на APP_PORT + Vite на :3000 с проксированием /api
pnpm test         vitest: shared + backend
pnpm typecheck    tsc --noEmit во всех пакетах
pnpm samples      сгенерировать демо-пары файлов
pnpm smoke        прогон пайплайна на демо-парах
```

Тесты не ходят в сеть: `fetch` подменяется заглушками. OCR-тесты опциональны:

```bat
set RUN_OCR_E2E=1 && pnpm --filter @recon/backend test
set RUN_SCAN_SMOKE=1 && pnpm smoke
```

Архитектура, соглашения и детали API описаны в [AGENTS.md](AGENTS.md).
