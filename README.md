# Reconciliation AI

Сверка актов сверки с контрагентами. **Локальная модель Ollama** — вариант по
умолчанию; удалённую OpenRouter можно выбрать в интерфейсе, ключ хранится в
браузере. Переносимое приложение для Windows: один процесс, один порт, никакого
Docker.

---

## Что нужно пользователю

1. **Ollama** — установленная и запущенная локальная модель. Обязательна, пока
   выбран локальный вариант. Если работаете на удалённой модели OpenRouter,
   Ollama не нужна.
2. **Папка приложения** — распакованная как есть (не через zip-архив).

Больше ничего: Node.js внутри приложения, установка зависимостей не требуется.

```bat
ollama pull qwen2.5:7b-instruct
```

Дальше — двойной клик по `start.cmd`. Интерфейс откроется сам.

---

## Настройка: `settings.txt`

Единственный файл конфигурации. Он лежит рядом с `start.cmd`.
Правьте его и перезапускайте приложение — больше нигде ничего менять не нужно.
Файла `.env` и переменных окружения больше не существует.

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `APP_HOST` | `127.0.0.1` | `127.0.0.1` — только с этой машины; `0.0.0.0` — доступ по сети |
| `APP_PORT` | `8080` | Порт приложения и интерфейса |
| `API_BASE_URL` | *(пусто)* | Адрес API для фронтенда. Пусто — запросы идут на тот же origin |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Адрес Ollama |
| `OLLAMA_MODEL` | `qwen2.5:7b-instruct` | Модель. Должна быть скачана: `ollama pull <имя>` |
| `AI_TIMEOUT_SEC` | `30` | Таймаут одного запроса к модели |
| `LOG_LEVEL` | `info` | `error` / `warn` / `info` / `debug` / `trace` |
| `LOG_FILE` | *(пусто)* | Например `logs/app.log`. Пусто — только консоль |
| `OPEN_BROWSER` | `true` | Открывать браузер при старте |

Ключа OpenRouter здесь нет и не будет: ключ хранится в браузере того, кто его
ввёл, и в `settings.txt` попасть не может. Неизвестный ключ по-прежнему роняет
старт с номером строки.

Формат — плоский список `КЛЮЧ=ЗНАЧЕНИЕ`. `#` в начале строки — комментарий,
`#` после пробела тоже считается комментарием. Ключи регистронезависимы.
Неизвестный ключ, некорректное число или неверный URL — приложение не стартует
с понятным сообщением, а не падает молча.

**Смена модели — двумя путями.**

*Локальная модель (по умолчанию).* Отредактируйте `OLLAMA_MODEL` в
`settings.txt`, выполните `ollama pull <новое имя>`, перезапустите `start.cmd`.

*Удалённая модель OpenRouter.* Шестерёнка в правом верхнем углу открывает окно
настроек модели: впишите идентификатор (например `vendor/model:free`) и API-ключ,
нажмите «Проверить подключение» — обе проверки бесплатные, кредит не списывается,
— и сохраните. Дальше ни файл, ни перезапуск не нужны: выбор применяется к
следующим запускам в обоих режимах.

Расхождение между настройкой и тем, что реально применилось, исключено иначе,
чем запретом выбора: значок в шапке называет модель, которая **ответила** на
текущий запуск, а пока никто не ответил — модель, которая уйдёт в следующий, и
оговорку об этом видно в подсказке при наведении. Он меняется сразу после
сохранения, без перезагрузки страницы.

Ключ живёт только в этом браузере. Он не попадает ни в `settings.txt`, ни в
`.env`, ни в лог, ни в отчёт, ни в ответы сервера. Поэтому:

- **ключ не переезжает вместе с папкой.** Скопировали `dist-portable/` на другую
  машину или в другой браузер — удалённого профиля там нет, работает локальная
  модель, и ключ придётся ввести заново;
- **два браузера на одном приложении работают на разных моделях** намеренно:
  выбор сделан в том браузере, где его сделали.

Цепочки запасных моделей нет: если удалённый ключ отвергнут, на счёте нет денег
или модели не существует, задание падает с названной причиной — молча уйти на
локальную модель нельзя, это была бы выдача чужого отчёта. Сетевая ошибка,
таймаут и перегрузка, наоборот, деградируют к эвристикам, как раньше.

## Режимы работы

Приложение открывается в режиме **«Сверка»** — полный пайплайн:

```
загрузка → разбор (включая OCR сканов) → определение структуры
   → подтверждение структуры → извлечение → сверка → анализ → отчёт
```

Если структура таблицы не распознаётся однозначно, пайплайн останавливается и
ждёт подтверждения: показывает колонки и предлагает, какая за что отвечает.
Прогресс и ход работы видны в реальном времени, задание можно отменить.

Готовый отчёт сохраняется и в `app/reports/`, и доступен из интерфейса:

- `GET /api/jobs/:id/report` — JSON
- `GET /api/jobs/:id/report.html` — HTML для печати и отправки

Второй режим — **«Быстро»**: два файла, разбор и сравнение на одной странице,
с ручным редактированием распознанных данных. Здесь работают только XLSX и PDF
с текстовым слоем; для сканов используйте режим «Сверка».

## Как это устроено

Один процесс Fastify отдаёт и API, и собранный фронтенд из того же origin —
поэтому в браузере интерфейс и API не расходятся по портам, и CORS-настройки
не нужны.

```
dist-portable/
  start.cmd            запуск (двойной клик)
  settings.txt         конфигурация
  README.txt           этот файл
  runtime/node.exe     встроенный Node
  frontend/dist/       собранный интерфейс
  app/                 backend
    src/               исходники TypeScript
    node_modules/      зависимости
    .tessdata/         языковые данные OCR
    logs/              логи
    reports/           отчёты
```

Backend запускается через `tsx` прямо из TypeScript: отделённой сборки
не требуется, а обновление — это замена папки `app/src`.

**Обновление по частям:**

- backend → заменить `app/src/`;
- интерфейс → собрать `pnpm --filter @recon/frontend build` и заменить `frontend/dist/`;
- `settings.txt`, `app/reports/`, `app/logs/` при этом не трогаются.

**Если модель недоступна** (Ollama не запущена или модель не скачана),
приложение не падает: структура определяется эвристиками, сверка считается
обычными правилами, а в лог и в интерфейс попадает причина деградации.
В консоль при старте выводится подсказка — `ollama serve` или `ollama pull`.
Это относится к локальной модели; та же деградация при сетевой ошибке, таймауте
или перегрузке работает и для удалённой.

Для удалённой модели правило другое, и разница неслучайная. Отказ, который
повтор исправит (сеть, таймаут, 429), деградирует к эвристикам, как локальная.
Отказ, который повтором не лечится, — падает задание с названной причиной:
отвергнутый ключ, нет денег на счёте, такой модели не существует. Смысл в том,
чтобы нельзя было получить отчёт по правилам, думая, что его посчитали удалённой
моделью: локальная модель молча согласилась бы, а деньги за платный вызов уже
ушли. Подробнее — в «Частые проблемы» ниже.

**Кто обработал документ.** Если запуск делала удалённая модель, отчёт — и JSON,
и HTML — содержит строку с провайдером и идентификатором модели. Это сделано
намеренно: отчёт уходит контрагенту, и он должен видеть, что документ
обрабатывала третья сторона. API-ключа в отчёте нет и быть не может. Отчёт,
сделанный локальной моделью, такой строки не содержит.

## Сборка portable-версии

Собирать нужно **на Windows** в корне репозитория, где есть Node.js 20+ и pnpm:

```bat
build-win.cmd
```

Скрипт установит зависимости, соберёт интерфейс, развернёт backend через
`pnpm deploy` (самодостаточная папка зависимостей без внешних ссылок),
скопирует встроенный `node.exe`, данные OCR и создаст `settings.txt`.
Результат — папка `dist-portable/`, которую копируют целиком.

> Папку нельзя распаковывать из zip-архива: в `node_modules` есть относительные
> ссылки нативных модулей. Переносите каталогом.

> **Вместе с папкой ключ не переезжает.** Он хранится в `localStorage` браузера
> того, кто его ввёл, и в `dist-portable/` его нет и быть не может: ключ,
> добавленный в настройки или в `.env`, уехал бы в копию папки на чужую машину.
> Тот, кому передали папку, получит локальную модель без всякой ошибки — и должен
> знать об этом заранее, а не удивляться отсутствию удалённого профиля. Свою
> машину он настраивает сам, ключ вводит сам.

## Частые проблемы

**Приложение работает, ошибок нет, но распознавание выглядит «тупо» — результаты
без AI, всё по эвристикам.**
Это не поломка, а штатная деградация (см. «Если модель недоступна» выше): пайплайн
считает эвристиками, и в интерфейсе это неотличимо от нормальной работы. Два
следа, по которым видно, что модели не было:

- **консоль при старте.** Preflight проверяет Ollama и модель до открытия браузера
  и печатает причину: `Ollama недоступна по адресу …`, `Ollama отвечает, но модель
  … не скачана` или `В Ollama пока нет ни одной модели` (`backend/src/preflight.ts`).
  Сообщение — в консоли и в лог, в интерфейс оно не выводится;
- **отчёт.** В обоих форматах (JSON и HTML) есть таймлайн логики `aiLogic`. При
  деградации в нём появляется шаг **«Гипотезы сформированы по правилам»** с
  уточнением, что модель была недоступна. Если такой шаг есть — AI не участвовал,
  арифметика сверки при этом корректна: правила детерминированные.

В интерфейсе других признаков нет: экран подтверждения структуры и отчёт не
показывают, кто определил структуру. Ориентируйтесь на эти два места.

Лечится на месте, пересборка не нужна: запустите Ollama, выполните `ollama pull`
с именем модели из `settings.txt`, перезапустите приложение. Скачанную модель
сверяйте через `ollama list` — имя в `settings.txt` должно совпадать с тегом
дословно, включая версию. Если удалённый профиль настроен, то же самое делает
не `settings.txt`, а окно настроек модели в шапке: сначала «Проверить
подключение» — оно называет причину, — потом сохранение.

**Ollama отвечает, но первый анализ идёт минуты.**
Это не зависание, а загрузка модели в память: на CPU 30–120 с. Последующие
запросы к той же модели быстрые. Полезное отличие: при недоступной модели анализ,
наоборот, подозрительно быстрый — соединение обрывается сразу.

**Задание упало с отказом удалённого шлюза.**
Это не поломка приложения: шлюз отказал, и приложение сказало об этом прямо,
вместо того чтобы посчитать всё по правилам и выдать это за работу модели.
Обычные сетевые ошибки и перегрузка так не выглядят — они деградируют, а не роняют
задание. Тот же отказ в окне настроек («Проверить подключение») звучит иначе: это
другая проверка, и она тоже бесплатная.

Какая именно формулировка в ошибке, определяет код ответа шлюза, а иногда — названный
им класс ошибки. На один и тот же отвергнутый ключ шлюз отвечает и «401», и «403»,
поэтому сверяйтесь по таблице, а не по одной строке:

| Формулировка в ошибке | Код ответа | Что это значит |
|---|---|---|
| Ключ OpenRouter отклонён провайдером | 401 | ключ не принят |
| Провайдер не разрешил запрос этому ключу | 403 | ключ не принят — на живом шлюзе именно так отвечало на фиктивный ключ |
| На счёте OpenRouter нет средств | 402 | на счёте пусто |
| Модель не найдена в каталоге OpenRouter | 404 | такого идентификатора в каталоге нет |
| OpenRouter отклонил запрос | 400, 422 или вовсе без кода | шлюз не назвал класс ошибки: смотрите текст после двоеточия |

В конце строки после двоеточия шлюз иногда добавляет своё объяснение (например
«Invalid API key») — оно и есть точная причина. Ключа API в тексте ошибки нет и быть
не может. Что делать:

- **отвергнут ключ** (`401` или `403`) — впишите его заново в окне настроек модели
  и нажмите «Проверить подключение». Проверка бесплатная, кредит не списывается;
- **нет денег на счёте** (`402`) — пополните счёт OpenRouter. Проверка покажет
  остаток кредита; у моделей с суффиксом `:free` кредит не нужен вовсе;
- **модель не найдена** (`404`) — идентификатор введён с опечаткой либо снят суффикс
  маршрутизации. Список моделей в интерфейсе не подставляется: проверка сама
  ищет идентификатор в каталоге и говорит, найден он или нет;
- **остальное** — прочитайте текст после двоеточия и проверьте подключение в том же
  окне: оно пересказывает причину своими словами и ничего не списывает;
- **вернуться к локальной модели** — одна кнопка в том же окне, ключ при этом
  стирается из браузера.

**В шапке локальная модель, а явно выбрана удалённая.**
Значок показывает не сохранённую настройку, а то, что реально работает: модель,
которая ответила на текущий запуск, а пока не ответил никто — профиль этого
браузера, с оговоркой в подсказке. Локальной моделью он **не заменяется** никогда
(см. выше про запрет молчаливого перехода): «локальная модель» в значке значит
ровно одно — профиль в этом браузере не задан, то есть ключа нет. Проверьте
«Проверить подключение» и вкладку, из которой запускали задание, — профиль
хранится в том браузере, где его сохранили, и в другой вкладке того же браузера
он тоже виден, а вот в другом браузере или на другой машине — нет.

## Разработка

```bat
pnpm install
pnpm dev          backend на APP_PORT + Vite на :3000 с проксированием /api
pnpm test         vitest: shared + backend
pnpm typecheck    tsc --noEmit во всех пакетах
pnpm samples      сгенерировать демо-пары файлов
pnpm smoke        прогон пайплайна на демо-парах
```

Тесты не ходят в сеть: `fetch` подменяется заглушками. OCR-тесты опциональны:

```bat
set RUN_OCR_E2E=1 && pnpm --filter @recon/backend test
set RUN_SCAN_SMOKE=1 && pnpm smoke
```

Архитектура, соглашения и детали API описаны в [AGENTS.md](AGENTS.md).
